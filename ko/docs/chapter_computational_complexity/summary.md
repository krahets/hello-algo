# 2.5 &nbsp; 요약

### 1. &nbsp; 핵심 정리

**알고리즘 효율 평가**

- 시간 효율과 공간 효율은 알고리즘을 평가하는 두 가지 주요 지표다.
- 실측으로 알고리즘의 효율을 평가할 수 있지만, 측정 환경의 영향을 없애기 어렵고 많은 컴퓨팅 자원이 든다.
- 복잡도 분석은 실측의 한계를 극복한다. 분석 결과를 모든 실행 플랫폼에 적용할 수 있고, 입력 크기가 달라질 때의 효율도 파악할 수 있다.

**시간 복잡도**

- 시간 복잡도는 입력 크기가 커질 때 실행 시간이 증가하는 추세를 나타내므로 알고리즘의 효율을 평가하는 데 유용하다. 다만 입력이 작거나 두 알고리즘의 시간 복잡도가 같으면 어느 쪽이 더 효율적인지 정확히 가리기 어렵다.
- 최악 시간 복잡도는 함수의 점근적 상한을 나타내는 빅 $O$ 표기법으로 표현한다. 이는 $n$이 양의 무한대로 갈 때 연산 횟수 $T(n)$의 증가 차수를 나타낸다.
- 시간 복잡도는 먼저 연산 횟수를 세고 그다음 점근적 상한을 구하는 두 단계로 추정한다.
- 대표적인 시간 복잡도를 낮은 것부터 나열하면 $O(1)$, $O(\log n)$, $O(n)$, $O(n \log n)$, $O(n^2)$, $O(2^n)$, $O(n!)$ 등이 있다.
- 어떤 알고리즘은 입력 데이터의 분포에 따라 시간 복잡도가 달라진다. 시간 복잡도는 최악, 최선, 평균 시간 복잡도로 나뉜다. 최선의 경우는 대개 입력이 엄격한 조건을 만족해야 하므로 최선 시간 복잡도는 거의 쓰지 않는다.
- 평균 시간 복잡도는 무작위 입력에서의 실행 효율을 나타내며 실제 응용에서의 성능에 가장 가깝다. 이를 구하려면 입력 데이터의 분포를 파악하고 각 경우를 종합해 기댓값을 계산해야 한다.

**공간 복잡도**

- 공간 복잡도는 시간 복잡도와 비슷하게 입력 크기가 커질 때 메모리 사용량이 증가하는 추세를 나타낸다.
- 실행에 관련된 메모리 공간은 입력 공간, 임시 공간, 출력 공간으로 나뉜다. 보통 입력 공간은 공간 복잡도 계산에서 제외한다. 임시 공간은 임시 데이터, 스택 프레임 공간, 명령어 공간으로 나뉘며, 이 중 스택 프레임 공간은 일반적으로 재귀 함수에서만 공간 복잡도에 영향을 준다.
- 일반적으로 최악 공간 복잡도만 고려한다. 즉, 공간을 가장 많이 쓰는 입력에서 실행 중 메모리 사용량이 가장 큰 시점을 기준으로 계산한다.
- 대표적인 공간 복잡도를 낮은 것부터 나열하면 $O(1)$, $O(\log n)$, $O(n)$, $O(n^2)$, $O(2^n)$ 등이 있다.

### 2. &nbsp; Q & A

**질문**: 꼬리 재귀의 공간 복잡도는 $O(1)$인가?

이론상 꼬리 재귀 함수의 공간 복잡도는 $O(1)$로 최적화할 수 있다. 하지만 대부분의 프로그래밍 언어(예를 들어 자바, 파이썬, C++, Go, C# 등)는 꼬리 재귀 자동 최적화를 지원하지 않으므로 보통 공간 복잡도를 $O(n)$으로 본다.

**질문**: 함수와 메서드라는 용어에는 어떤 차이가 있는가?

<u>함수(function)</u>는 독립적으로 실행할 수 있으며 모든 인수를 명시적으로 전달한다. <u>메서드(method)</u>는 객체에 연결되어 있다. 호출한 객체가 암묵적으로 전달되므로 해당 인스턴스의 데이터를 다룰 수 있다.

몇 가지 대표적인 프로그래밍 언어를 예로 살펴보자.

- C는 절차적 프로그래밍 언어로 객체 지향 개념을 내장하지 않아 함수만 있다. 다만 구조체(struct)를 만들어 객체 지향 프로그래밍을 흉내 낼 수 있다. 이때 구조체와 연결된 함수는 다른 언어의 메서드에 해당한다.
- 자바와 C#은 객체 지향 언어로, 코드 블록인 메서드는 보통 클래스에 속한다. 정적 메서드는 클래스에 연결되어 특정 인스턴스의 변수에 직접 접근할 수 없으므로 함수처럼 동작한다.
- C++와 파이썬은 절차적 프로그래밍(함수)과 객체 지향 프로그래밍(메서드)을 모두 지원한다.

**질문**: ‘대표적인 공간 복잡도 유형’ 그림은 실제 공간 사용량의 절댓값을 보여 주는가?

아니다. 이 그림은 공간 복잡도, 즉 실제 사용량의 절댓값이 아닌 증가 추세를 보여 준다.

$n = 8$일 때를 보면 각 곡선의 값이 해당 함수의 값과 맞지 않을 수 있다. 각 곡선에 상수항을 넣어 값의 범위를 보기 좋게 압축했기 때문이다.

실제로는 각 방법의 복잡도에 포함된 ‘상수항’을 모르는 경우가 많아 $n = 8$일 때 복잡도만으로 최적의 해법을 고르기는 어렵다. 하지만 $n = 8^5$일 때는 증가 추세의 영향이 지배적이므로 선택하기가 훨씬 쉽다.

**질문**: 실제 사용 환경에 따라 시간이나 공간을 양보하는 방식으로 알고리즘을 설계하기도 하는가?

실제로는 대개 공간을 더 써서 시간을 줄인다. 예를 들어 데이터베이스에 B+ 트리 인덱스나 해시 인덱스를 만들면 메모리를 많이 쓰는 대신 $O(\log n)$, 심지어 $O(1)$의 시간에 효율적으로 조회할 수 있다.

공간이 귀한 환경에서는 시간을 더 들여 공간을 아끼기도 한다. 예를 들어 임베디드 개발에서는 기기의 메모리가 귀하므로 해시 테이블 대신 배열을 순차 탐색하는 방법을 택할 수 있다. 메모리 사용량은 줄지만 탐색은 느려진다.
