# 요약

### 핵심 내용

- 배열과 연결 리스트는 컴퓨터 메모리에 데이터를 저장하는 두 방식, 즉 연속 공간 저장과 분산 공간 저장을 각각 대표하는 기본 자료 구조이다. 둘의 특성은 서로 보완적이다.
- 배열은 임의 접근을 지원하고 메모리를 적게 차지한다. 하지만 원소의 삽입과 삭제 효율이 낮고 초기화한 뒤에는 길이를 바꿀 수 없다.
- 연결 리스트는 참조(포인터)를 바꿔 노드를 효율적으로 삽입하고 삭제하며 길이도 유연하게 조절한다. 하지만 노드 접근 효율이 낮고 메모리를 많이 차지한다. 대표적인 유형은 단일 연결 리스트, 원형 연결 리스트, 이중 연결 리스트이다.
- 리스트는 원소의 추가, 삭제, 탐색, 수정을 지원하는 순서 있는 모음이며, 보통 동적 배열로 구현한다. 배열의 장점을 유지하면서 길이를 유연하게 조절할 수 있다.
- 리스트의 등장으로 배열의 실용성이 크게 높아졌지만 메모리 공간 일부를 낭비할 수 있다.
- 프로그램 실행 중 데이터는 주로 메모리에 저장된다. 배열은 메모리 공간 효율이 더 높고, 연결 리스트는 메모리를 더 유연하게 사용한다.
- 캐시는 캐시 라인과 프리페치, 공간 지역성과 시간 지역성을 활용해 데이터를 불러온다. CPU가 데이터에 빠르게 접근할 수 있어 프로그램 실행 효율이 크게 높아진다.
- 배열은 캐시 적중률이 더 높아 대체로 연결 리스트보다 효율적이다. 자료 구조는 구체적인 요구와 상황에 맞춰 선택해야 한다.

### Q & A

**Q**: 배열을 스택에 저장하는 경우와 힙에 저장하는 경우에 시간 효율과 공간 효율이 달라지는가?

스택에 있든 힙에 있든 배열은 연속된 메모리 공간에 저장되므로 데이터를 조작하는 효율은 대체로 같다. 다만 스택과 힙 자체의 특성 때문에 다음과 같은 차이가 생긴다.

1. 할당 및 해제 효율: 스택은 크기가 작은 메모리 영역이며 컴파일러가 자동으로 할당을 처리한다. 힙은 상대적으로 크고 코드에서 동적으로 할당할 수 있으며 단편화되기 쉽다. 그래서 보통 힙에서의 할당과 해제가 스택에서보다 느리다.
2. 크기 제한: 스택 메모리는 비교적 작고, 힙 크기는 일반적으로 사용 가능한 메모리에 의해 제한된다. 따라서 큰 배열을 저장할 때는 힙이 더 적합하다.
3. 유연성: 스택에 놓이는 배열의 크기는 컴파일 시점에 정해야 하지만 힙에 놓이는 배열의 크기는 실행 시점에 동적으로 정할 수 있다.

**Q**: 배열은 원소의 자료형이 같아야 하는데, 연결 리스트에서는 왜 같은 자료형이어야 한다는 점을 강조하지 않는가?

연결 리스트는 노드로 이루어지고 노드 사이를 참조(포인터)로 연결한다. 따라서 노드마다 `int`, `double`, `string`, `object` 등 다른 자료형의 데이터를 저장할 수 있다.

반면 배열은 오프셋을 계산해 원소 위치를 구하려면 원소의 자료형이 같아야 한다. 예를 들어 배열에 `int`와 `long`이 함께 들어 있고 각 원소가 각각 4바이트와 8바이트를 차지한다면 다음 공식으로 오프셋을 계산할 수 없다. 배열에 ‘원소 크기’가 두 종류이기 때문이다.

```shell
# 원소의 메모리 주소 = 배열의 메모리 주소(첫 원소의 메모리 주소) + 원소 크기 * 원소 인덱스
```

**Q**: 노드 `P`를 삭제한 뒤 `P.next`를 `None`으로 설정해야 하는가?

`P.next`를 바꾸지 않아도 된다. 이 리스트에서 보면 머리부터 꼬리까지 순회해도 더는 `P`를 만나지 않는다. 즉 노드 `P`는 이미 리스트에서 삭제되었으므로 노드 `P`가 어디를 가리키든 리스트에는 영향이 없다.

자료 구조와 알고리즘 문제를 풀 때는 프로그램의 논리만 올바르다면 연결을 끊지 않아도 된다. 표준 라이브러리에서는 연결을 끊는 편이 더 안전하고 논리도 명확하다. 연결을 끊지 않은 상태에서 삭제한 노드의 메모리가 정상적으로 회수되지 않으면 후속 노드의 메모리 회수에도 영향을 준다.

**Q**: 연결 리스트에서 삽입과 삭제의 시간 복잡도는 $O(1)$이다. 그런데 추가하거나 삭제하기 전에 원소를 찾는 데 $O(n)$ 시간이 필요하다면 왜 시간 복잡도가 $O(n)$이 아닌가?

먼저 원소를 찾은 뒤 삭제한다면 시간 복잡도는 실제로 $O(n)$이다. 하지만 연결 리스트에서 $O(1)$ 시간에 삽입하고 삭제할 수 있다는 장점은 다른 용도에서 드러난다. 예를 들어 덱은 연결 리스트로 구현하기 좋다. 머리 노드와 꼬리 노드를 항상 가리키는 포인터를 유지하면 매번 삽입과 삭제를 $O(1)$ 시간에 할 수 있다.

**Q**: ‘연결 리스트의 정의와 저장 방식’ 그림에서 옅은 파란색으로 나타낸 노드 포인터는 한 칸의 메모리 주소를 차지하는가? 아니면 노드 값과 공간을 절반씩 나누어 쓰는가?

그림은 개념을 보여 줄 뿐이다. 실제 크기는 구체적인 상황에 따라 따져야 한다.

- 노드 값이 차지하는 공간은 `int`, `long`, `double`, 인스턴스 객체 등 자료형에 따라 다르다.
- 포인터 변수가 차지하는 메모리 크기는 운영체제와 컴파일 환경에 따라 달라지며 대부분 8바이트 또는 4바이트이다.

**Q**: 리스트 끝에 원소를 추가하는 연산은 언제나 $O(1)$인가?

원소를 추가할 공간이 부족하면 먼저 리스트 용량을 늘린 다음 추가해야 한다. 시스템이 새 메모리 블록을 할당하고 기존 리스트의 모든 원소를 옮겨야 하므로 이때의 시간 복잡도는 $O(n)$이다.

**Q**: “리스트의 등장으로 배열의 실용성이 크게 높아졌지만 메모리 공간 일부를 낭비할 수 있다”에서 공간 낭비란 용량, 길이, 확장 배수처럼 추가로 둔 변수가 차지하는 메모리인가?

여기서 말하는 공간 낭비에는 주로 두 가지가 있다. 첫째, 리스트에는 초기 길이가 정해져 있지만 실제로는 그만큼 필요하지 않을 수 있다. 둘째, 잦은 확장을 피하려고 보통 용량에 일정한 계수를 곱한다(예: $\times 1.5$). 그러면 빈자리가 많이 생기는데, 보통은 그 자리를 다 채우지 못한다.

**Q**: Python에서 `n = [1, 2, 3]`로 초기화하면 세 원소의 주소가 연속된다. 그런데 `m = [2, 1, 3]`로 초기화하면 각 원소의 id는 연속되지 않고 각각 `n`에 있는 같은 원소의 id와 일치한다. 이처럼 원소의 주소가 연속되지 않아도 `m`은 배열인가?

리스트 원소를 연결 리스트의 노드로 바꿔 `n = [n1, n2, n3, n4, n5]`로 두면, 보통 이 다섯 노드 객체도 메모리 곳곳에 흩어져 있다. 그래도 리스트 인덱스가 주어지면 $O(1)$ 시간에 노드의 메모리 주소를 얻어 해당 노드에 접근할 수 있다. 배열이 저장하는 것은 노드 자체가 아니라 노드의 참조이기 때문이다.

여러 다른 언어와 달리 Python에서는 숫자도 객체로 감싼다. 리스트에 저장되는 것은 숫자 자체가 아니라 그 숫자의 참조이다. 그래서 두 배열에 있는 같은 숫자가 같은 id를 가지며, 이 숫자들의 메모리 주소는 연속될 필요가 없다.

**Q**: C++ STL에는 이중 연결 리스트를 구현한 `std::list`가 이미 있는데, 일부 알고리즘 책은 이를 직접 쓰는 일이 드문 듯하다. 어떤 한계가 있어서인가?

우선 알고리즘은 배열로 구현하는 것을 선호하고 연결 리스트는 필요한 경우에만 쓰는 편이다. 주된 이유는 두 가지이다.

- 공간 비용: 원소마다 포인터 두 개(이전 원소용 하나, 다음 원소용 하나)가 추가로 필요하므로 보통 `std::list`가 `std::vector`보다 공간을 더 차지한다.
- 낮은 캐시 효율: 데이터가 연속해서 저장되지 않아 `std::list`의 캐시 활용도가 낮다. 보통은 `std::vector`의 성능이 더 좋다.

또한 연결 리스트가 주로 필요한 경우는 이진 트리와 그래프이다. 스택이나 큐를 다룰 때는 연결 리스트보다 언어에서 제공하는 `stack`과 `queue`를 쓰는 경우가 많다.

**Q**: `res = [[0]] * n` 연산으로 만든 이차원 리스트에서 각각의 `[0]`은 서로 독립적인가?

독립적이지 않다. 이 이차원 리스트의 모든 `[0]`은 실제로 같은 객체의 참조이다. 그중 한 원소를 수정하면 그에 대응하는 모든 원소가 함께 바뀐다.

이차원 리스트에서 각 `[0]`이 독립적이어야 한다면 `res = [[0] for _ in range(n)]`을 사용하면 된다. 이 방법은 서로 독립적인 `[0]` 리스트 객체를 $n$개 초기화한다.

**Q**: `res = [0] * n` 연산으로 만든 리스트에서 각각의 정수 0은 독립적인가?

이 리스트에서 모든 정수 0은 같은 객체의 참조이다. Python은 작은 정수(보통 -5부터 256까지)를 캐시 풀에 보관해 객체 재사용을 극대화하고 성능을 높이기 때문이다.

같은 객체를 가리키더라도 리스트의 각 원소는 독립적으로 바꿀 수 있다. Python의 정수는 ‘불변 객체’이기 때문이다. 원소를 수정하는 것은 원래 객체 자체를 바꾸는 것이 아니라 다른 객체에 대한 참조로 교체하는 것이다.

하지만 리스트의 원소가 리스트, 딕셔너리, 클래스 인스턴스 같은 ‘가변 객체’일 때 원소의 내용을 수정하면 그 객체 자체가 바뀐다. 그러면 그 객체를 참조하는 모든 원소에서 같은 변화가 나타난다.
