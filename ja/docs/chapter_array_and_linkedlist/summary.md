# 4.5 &nbsp; まとめ

### 1. &nbsp; 要点の振り返り

- 配列と連結リストは基本的なデータ構造で、それぞれコンピュータのメモリ上で連続した領域に格納する方法と、分散した領域に格納する方法を代表しています。両者の特徴には互いを補う関係があります。
- 配列はランダムアクセスが可能で、使うメモリも比較的少なく済みます。ただし、要素の挿入と削除の効率は低く、初期化後に長さを変えられません。
- 連結リストは、参照（ポインタ）を書き換えるだけでノードを効率よく挿入・削除でき、長さも柔軟に調整できます。一方、指定位置のノードへのアクセス効率は低く、メモリを多く使います。代表的な種類には、単方向連結リスト、循環連結リスト、双方向連結リストがあります。
- リストは、要素の追加、削除、探索、変更ができる順序付きの集まりです。通常は動的配列で実装し、配列の利点を保ちながら長さを柔軟に調整できます。
- リストによって配列は格段に使いやすくなりますが、メモリ領域の一部が無駄になることがあります。
- プログラムの実行中、データは主にメモリに格納されます。配列はメモリの空間効率に優れ、連結リストはメモリをより柔軟に使えます。
- キャッシュは、キャッシュラインやプリフェッチを使い、空間的局所性や時間的局所性を利用してデータを読み込みます。その結果、CPU は高速にデータにアクセスでき、プログラムの実行効率が大きく向上します。
- 配列はキャッシュヒット率が高いため、一般に連結リストより効率的です。データ構造は具体的な要件や利用場面に合わせて選びましょう。

### 2. &nbsp; Q & A

**Q**：配列をスタックに置くかヒープに置くかで、時間効率や空間効率は変わりますか。

スタックでもヒープでも、配列は連続したメモリ領域に格納されるので、データを操作する効率はほぼ同じです。ただし、スタックとヒープ自体の性質により、次の点に違いがあります。

1. 確保と解放の効率：スタックは比較的小さなメモリ領域で、コンパイラが自動的に割り当てます。ヒープは比較的大きく、コード内で動的に確保できる一方で断片化しやすい領域です。そのため、ヒープでの確保と解放は通常スタックよりも低速です。
2. 大きさの制限：スタックの領域は比較的小さく、ヒープの大きさは一般に使用可能なメモリ量で制限されます。このため、大きな配列の格納にはヒープのほうが適しています。
3. 柔軟性：スタック上の配列の大きさはコンパイル時に決める必要がありますが、ヒープ上の配列の大きさは実行時に動的に決められます。

**Q**：配列では要素が同じ型であることを求めるのに、連結リストでは同じ型であることを強調しないのはなぜですか。

連結リストを構成するノードは参照（ポインタ）でつながっています。各ノードは、たとえば `int`、`double`、`string`、`object` など、異なる型のデータを格納できます。

これに対し、配列の要素は同じ型である必要があります。そうすれば、オフセットを計算して目的の要素の位置を求められます。たとえば、配列に `int` と `long` が混在し、それぞれ 1 要素が 4 バイトと 8 バイトを占めるとします。「要素の長さ」が 2 通りあるため、次の式ではオフセットを計算できません。

```shell
# 要素のメモリアドレス = 配列のメモリアドレス（先頭要素のメモリアドレス） + 要素の長さ * 要素のインデックス
```

**Q**：ノード `P` を削除した後、`P.next` を `None` にする必要はありますか。

`P.next` を書き換えなくてもかまいません。このリストの先頭から末尾までたどっても、もう `P` を通りません。つまりノード `P` はリストから削除されており、`P` がどこを指していても、このリストには影響しません。

データ構造やアルゴリズムの問題を解くうえでは、プログラムの論理が正しければ参照を切らなくても問題ありません。標準ライブラリを実装する立場では、切ったほうが安全で意図も明確です。参照を残したまま、削除したノードが正しく回収されずに残ると、後続ノードのメモリ回収にも影響します。

**Q**：連結リストの挿入と削除の時間計算量は $O(1)$ とのことですが、その前に要素を探すのに $O(n)$ の時間がかかるなら、なぜ時間計算量は $O(n)$ ではないのですか。

要素を探してから削除するのであれば、確かに時間計算量は $O(n)$ です。一方、$O(1)$ で挿入・削除できる利点が生きる用途もあります。たとえば、両端キューは連結リストでの実装に適しています。常に先頭と末尾を指すポインタを保持しておけば、各挿入・削除は $O(1)$ で済みます。

**Q**：図「連結リストの定義と格納方法」で、水色で示されたノードのポインタは、メモリアドレス 1 つ分の領域を占めるのですか。それとも、ノードの値と半分ずつ領域を使うのですか。

図は仕組みを模式的に示したものです。実際のサイズは具体的な条件に即して考える必要があります。

- ノードの値が占める領域は型によって異なります。たとえば `int`、`long`、`double`、クラスのインスタンスなどでは必要な領域が異なります。
- ポインタ変数の大きさは OS やコンパイル環境によって決まり、多くの場合は 8 バイトまたは 4 バイトです。

**Q**：リストの末尾に要素を追加するとき、時間計算量は毎回必ず $O(1)$ ですか。

追加しようとした要素がリストに収まらなければ、先に容量を増やします。システムが新しいメモリ領域を確保し、元のリストの全要素を移すので、このときの時間計算量は $O(n)$ です。

**Q**：「リストによって配列は格段に使いやすくなりますが、メモリ領域の一部が無駄になることがあります」とあります。無駄になる領域とは、容量、長さ、拡張倍率などの追加の変数が使うメモリのことですか。

ここでいう無駄は主に 2 種類あります。まず、リストには初期の長さを設定しますが、その分を使い切るとは限りません。また、頻繁な拡張を避けるため、容量を増やすときは通常、一定の係数を掛けます（たとえば $\times 1.5$）。その結果、多くの空きが生じ、通常はすべてを埋め切れません。

**Q**：Python で `n = [1, 2, 3]` と初期化すると 3 要素のアドレスは連続しています。ところが `m = [2, 1, 3]` と初期化すると、各要素の id は連続せず、`n` の同じ値の要素とそれぞれ一致します。要素のアドレスが連続していなくても、`m` は配列なのでしょうか。

リストの要素を連結リストのノードに置き換えて `n = [n1, n2, n3, n4, n5]` とした場合も、通常 5 つのノードオブジェクトはメモリ上に分散して格納されます。それでもリストのインデックスがわかれば、$O(1)$ 時間でノードのメモリアドレスを取得して、そのノードにアクセスできます。配列に格納されているのはノードそのものではなく、ノードへの参照だからです。

多くの言語とは異なり、Python では数値もオブジェクトとして扱います。リストに格納するのは数値そのものではなく、数値への参照です。そのため、この 2 つの配列では、同じ数値は同じ id を持ちますが、数値のメモリアドレスが連続している必要はありません。

**Q**：C++ の STL には双方向連結リストを実装した `std::list` がありますが、アルゴリズムの本ではあまり直接使われないようです。何か制約があるのでしょうか。

一つには、アルゴリズムの実装では配列を優先し、連結リストは必要なときだけ使う傾向があります。主な理由は 2 つです。

- 領域のコスト：各要素に前後の要素を指すポインタが 1 本ずつ、合わせて 2 本余分に必要なので、通常 `std::list` は `std::vector` よりも多くの領域を使います。
- キャッシュ効率：データが連続して並んでいないため、`std::list` はキャッシュを効率的に使えません。一般には `std::vector` のほうが高い性能を得られます。

もう一つには、連結リストが必要になる主な場面は二分木とグラフです。スタックやキューには、連結リストを直接使うよりも、言語が提供する `stack` や `queue` を使うことが多いからです。

**Q**：`res = [[0]] * n` で二次元リストを作ると、それぞれの `[0]` は独立していますか。

独立していません。この二次元リストでは、すべての `[0]` が実際には同じオブジェクトへの参照です。どれか 1 つの中身を書き換えると、ほかのすべての対応する要素にも同じ変更が現れます。

二次元リストの各 `[0]` を独立させたい場合は、`res = [[0] for _ in range(n)]` と書けます。この書き方では $n$ 個の独立した `[0]` リストオブジェクトを初期化します。

**Q**：`res = [0] * n` でリストを作ると、それぞれの整数 0 は独立していますか。

このリストでは、すべての整数 0 は同じオブジェクトへの参照です。Python では、小さな整数（通常は -5 から 256 まで）をキャッシュしてオブジェクトをできるだけ再利用し、性能を高めているためです。

各要素が同じオブジェクトを指していても、リストの要素は個別に書き換えられます。Python の整数は「イミュータブル（変更不能）なオブジェクト」だからです。要素を書き換えると、元のオブジェクト自体は変わらず、参照先が別のオブジェクトに切り替わります。

一方、要素がリスト、辞書、クラスのインスタンスなどの「ミュータブル（変更可能）なオブジェクト」で、その中身を書き換えると、オブジェクト自体が変わります。そのオブジェクトを参照するすべての要素に同じ変更が現れます。
