# 2.5 &nbsp; まとめ

### 1. &nbsp; 要点の振り返り

**アルゴリズムの効率の評価**

- 時間効率と空間効率は、アルゴリズムの良し悪しを測る 2 つの主な指標です。
- 実測によって効率を評価できますが、測定環境の影響を取り除くのは難しく、多くの計算資源も必要です。
- 計算量解析なら実測のこうした制約を避けられます。分析結果はどの実行環境にも適用でき、データサイズに応じたアルゴリズムの効率を明らかにできます。

**時間計算量**

- 時間計算量は、データ量が増えると実行時間がどのように増えるかを示し、効率の評価に役立ちます。ただし、入力データが小さいときや時間計算量が等しいときなどには、どちらが効率的かを正確に比較できません。
- 最悪時間計算量は大文字の $O$ を使った記法で表し、関数の漸近的上界に対応します。$n$ を正の無限大に近づけたときの操作回数 $T(n)$ の増加のオーダーを表します。
- 時間計算量は、まず操作回数を数え、次に漸近的上界を求めるという 2 段階で見積もります。
- 代表的な時間計算量を小さい順に並べると、$O(1)$、$O(\log n)$、$O(n)$、$O(n \log n)$、$O(n^2)$、$O(2^n)$、$O(n!)$ などがあります。
- アルゴリズムによっては、時間計算量が入力データの分布に左右されます。最悪、最良、平均の時間計算量を区別しますが、最良の場合が起こるには通常、入力が厳しい条件を満たす必要があるため、最良時間計算量はほとんど使いません。
- 平均時間計算量はランダムな入力に対する実行効率を表し、実際の利用時の性能に最も近い指標です。求めるには、入力データの分布を調べ、各場合を合わせた期待値を計算します。

**空間計算量**

- 空間計算量は時間計算量と同様に、データ量が増えるとメモリ使用量がどのように増えるかを表します。
- 実行時のメモリは入力領域、作業領域、出力領域に分けられ、通常は入力領域を空間計算量に含めません。作業領域は一時データ、スタックフレーム領域、命令領域に分けられます。このうちスタックフレーム領域が空間計算量に影響するのは、通常は再帰関数の場合です。
- 通常は最悪空間計算量だけを考えます。つまり、メモリを最も多く使う入力について、実行中に使用量が最大となる時点を調べます。
- 代表的な空間計算量を小さい順に並べると、$O(1)$、$O(\log n)$、$O(n)$、$O(n^2)$、$O(2^n)$ などがあります。

### 2. &nbsp; Q & A

**Q**：末尾再帰の空間計算量は $O(1)$ ですか。

理論上、末尾再帰関数の空間計算量は $O(1)$ に最適化できます。ただし、大半のプログラミング言語（Java、Python、C++、Go、C# など）は末尾再帰の自動最適化に対応していないため、通常は $O(n)$ と考えます。

**Q**：関数とメソッドという用語には、どのような違いがありますか。

<u>関数（function）</u>は単独で実行でき、引数はすべて明示的に渡されます。<u>メソッド（method）</u>はオブジェクトに結び付いており、呼び出し時にそのオブジェクトとの対応が暗黙に与えられるため、クラスのインスタンスが持つデータを操作できます。

よく使われるプログラミング言語をいくつか例に見てみましょう。

- C は手続き型の言語で、オブジェクト指向の概念を持たないので、あるのは関数だけです。ただし、構造体（struct）を作ればオブジェクト指向の書き方を模擬できます。構造体と関連付けた関数が、ほかの言語のメソッドに相当します。
- Java と C# はオブジェクト指向言語で、処理をまとめたコード（メソッド）は通常クラスの一部です。静的メソッドはクラスに結び付き、特定のインスタンス変数に直接アクセスできないので、関数のように振る舞います。
- C++ と Python は、手続き型プログラミング（関数）とオブジェクト指向プログラミング（メソッド）の両方に対応しています。

**Q**：「代表的な空間計算量」の図は、使用する領域の絶対的な大きさを示していますか。

いいえ。この図が示す空間計算量は、メモリ使用量の絶対値ではなく、その増え方を表します。

例えば $n = 8$ の位置を見ると、各曲線の値が対応する関数の値と一致しないことに気づくかもしれません。各曲線には、値を見やすい範囲に収めるための定数項が含まれているからです。

実際には、それぞれの手法の計算量に含まれる「定数項」はたいていわからないため、$n = 8$ のときに最もよい解法を計算量だけで選ぶのは一般に困難です。一方、$n = 8^5$ なら増え方の違いが支配的になるので、ずっと選びやすくなります。

**Q**：実際の用途に合わせて、時間やメモリの一方を犠牲にしてアルゴリズムを設計することはありますか。

実際には、メモリを多く使って時間を節約することがほとんどです。例えばデータベースでは、B+ 木やハッシュによるインデックスを作るのが一般的です。多くのメモリを使う代わりに、$O(\log n)$、あるいは $O(1)$ で高速に検索できます。

メモリが貴重な場面では、時間をかけてメモリを節約することもあります。例えば組み込み開発では、機器のメモリに余裕がないため、ハッシュテーブルを使わず配列を順に探索することがあります。メモリを節約できる代わりに、探索は遅くなります。
