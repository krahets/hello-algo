# 2.5 &nbsp; 本章小結

### 1. &nbsp; 重點回顧

**評估演算法效率**

- 時間效率與空間效率是衡量演算法優劣的兩項主要指標。
- 我們可以透過實際測試評估演算法效率，但很難排除測試環境的影響，而且測試會耗費大量運算資源。
- 複雜度分析能克服實際測試的限制。分析結果適用於各種執行平台，也能呈現演算法在不同資料規模下的效率。

**時間複雜度**

- 時間複雜度用來衡量資料量增加時，演算法的執行時間如何成長。這種評估方式很有效，但也有其限制。例如，輸入資料量較小或兩個演算法的時間複雜度相同時，光靠時間複雜度就無法精確判斷哪一個較有效率。
- 最差時間複雜度以大 $O$ 記號表示，對應函數的漸近上界，反映當 $n$ 趨近正無窮大時，操作次數 $T(n)$ 的成長階數。
- 推算時間複雜度有兩個步驟：先計算操作次數，再判斷漸近上界。
- 常見的時間複雜度由低到高依序有 $O(1)$、$O(\log n)$、$O(n)$、$O(n \log n)$、$O(n^2)$、$O(2^n)$ 與 $O(n!)$ 等。
- 有些演算法的時間複雜度並非固定，而是取決於輸入資料的分布。時間複雜度可分為最差、最佳與平均三種。最佳時間複雜度很少使用，因為輸入資料通常必須滿足嚴格的條件，才會出現最佳情況。
- 平均時間複雜度反映隨機輸入資料時演算法的執行效率，最接近實際應用的效能。計算時必須考量輸入資料的分布，並據此求出操作次數的期望值。

**空間複雜度**

- 空間複雜度與時間複雜度的作用相似，用來衡量資料量增加時，演算法占用的記憶體空間如何成長。
- 演算法執行時的記憶體空間可分為輸入空間、暫存空間與輸出空間。計算空間複雜度時，通常不計入輸入空間。暫存空間又可分為暫存資料、堆疊框架空間與指令空間，其中堆疊框架空間通常只在遞迴函式中影響空間複雜度。
- 我們通常只關心最差空間複雜度，也就是針對最差情況的輸入，計算執行期間空間用量最高時的複雜度。
- 常見的空間複雜度由低到高依序有 $O(1)$、$O(\log n)$、$O(n)$、$O(n^2)$ 與 $O(2^n)$ 等。

### 2. &nbsp; Q & A

**Q**：尾端遞迴的空間複雜度是 $O(1)$ 嗎？

理論上，尾端遞迴函式的空間複雜度可以降到 $O(1)$。不過，絕大多數程式語言（例如 Java、Python、C++、Go、C# 等）不支援自動進行尾端遞迴最佳化，因此通常將其空間複雜度視為 $O(n)$。

**Q**：「函式」與「方法」這兩個術語有什麼不同？

<u>函式（function）</u>可以獨立執行，所有參數都明確傳入。<u>方法（method）</u>則與物件相關聯，呼叫方法的物件會隱含地傳入，讓方法能操作該類別實例中的資料。

以下以幾種常見的程式語言為例說明。

- C 是程序式程式語言，沒有內建物件導向的概念，因此只有函式。不過，我們可以建立結構體（struct）來模擬物件導向程式設計，與結構體相關聯的函式就相當於其他語言中的方法。
- Java 與 C# 是物件導向程式語言，程式碼區塊（方法）通常是某個類別的一部分。靜態方法的行為類似函式，因為它繫結到類別，無法直接存取特定實例的變數。
- C++ 與 Python 同時支援程序式程式設計（函式）和物件導向程式設計（方法）。

**Q**：「常見的空間複雜度類型」這張圖表示的是空間用量的絕對大小嗎？

不是。圖中呈現的是空間複雜度，反映空間用量的成長趨勢，並未指出實際占用多少空間。

假設取 $n = 8$，你可能會發現各條曲線的數值與對應的函數值不相符。這是因為每條曲線都帶有一個常數項，把數值範圍壓縮到適合呈現在圖上的大小。

實務上，我們通常不知道每種做法在複雜度中省略的「常數項」有多大，因此一般無法單憑複雜度判斷在 $n = 8$ 的情況下哪種解法最好。到了 $n = 8^5$ 就容易選擇，因為成長趨勢已經成為主導因素。

**Q**：設計演算法時，會依實際使用情境選擇犧牲時間或空間嗎？

在實際應用中，多數情況會選擇以空間換時間。例如，資料庫常建立 B+ 樹或雜湊索引，雖然占用大量記憶體空間，卻能換來 $O(\log n)$ 甚至 $O(1)$ 的查詢效率。

當空間資源有限時，也會選擇以時間換空間。例如，嵌入式裝置的記憶體很寶貴，工程師可能捨棄雜湊表，改為依序搜尋陣列，以較慢的搜尋速度換取較低的記憶體用量。
